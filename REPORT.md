# Отчёт по проекту: параллельная обработка изображений

Дата: 18 ноября 2026 года.

## Цель проекта

Программа читает BMP, применяет фильтры и записывает результат.
Задача — сравнить последовательное выполнение с многопоточным и выяснить,
как размер изображения, число потоков и порядок обработки папки влияют на время.
Основание — файл «Заявка_коллективный_проект.pdf» в репозитории.

## Как устроена программа

`Image` хранит ширину, высоту и байты пикселей BGR. BMP-кодек отвечает только
за файлы. `Transformation` применяет один фильтр. `Pipeline` хранит цепочку
преобразований и выбирает порядок её выполнения. Модуль `batch` обрабатывает
каталог и измеряет время. `main.cpp` разбирает команды и выводит ошибки.

Такое разделение позволяет менять фильтры, порядок выполнения и работу с файлами
по отдельности. Дополнительных библиотек изображений и сложной иерархии классов нет.

### Фильтры

- **Размытие:** для каждого канала берётся среднее девяти пикселей окна 3×3.
- **Резкость:** центральный пиксель умножается на 5, затем вычитаются четыре
  прямых соседа. Результат ограничивается диапазоном 0…255.
- **Серый:** среднее трёх каналов записывается во все каналы пикселя.

- **Экспозиция +1 EV** удваивает значение каждого канала с ограничением до 255.
- **Контуры** вычисляют для каждого канала разность между значением центрального пикселя, умноженным на 8, и суммой восьми соседей. Результат ограничивается диапазоном 0…255.

Порядок этапов во всех трёх режимах: размытие → резкость → серый → экспозиция → контуры.

На краях изображения используется ближайший пиксель внутри кадра.
Преобразование в серый не использует окно 3×3, поскольку ему достаточно одного пикселя.

### Что выполняется параллельно

При обработке одного фильтра изображение делится на непересекающиеся полосы
строк. Каждый поток читает общий исходник и записывает только свою полосу
в отдельный буфер. Соседние полосы можно читать для свёртки; конфликтов записи нет.
Перед следующим преобразованием программа дожидается завершения всех полос.

В `file-first` вся цепочка применяется к одному изображению, затем к следующему.
В `stage-first` сначала один фильтр применяется ко всем изображениям, затем следующий.
В обоих случаях потоки делят строки отдельного кадра.

В `pipeline` работники берут из очереди задачи «изображение + этап». Следующий
этап изображения доступен только после предыдущего. Разные изображения могут
одновременно проходить разные фильтры. Конвейер создаёт `min(p, число изображений)` рабочих потоков,
где `p` — запрошенное число потоков. Для двух кадров при `p = 8` работают два потока.
Каждый из них выполняет этап для целого кадра. Этапы назначаются динамически, отдельного потока на каждый фильтр нет.
На одном изображении этот режим не даёт параллелизма между этапами.

## Как проверена правильность

Проект собран компилятором Visual Studio с оптимизацией `/O2`.
Автоматические проверки сравнивают пиксели с независимым расчётом на Python.
Проверены отдельные фильтры и цепочка во всех трёх режимах, разные числа потоков,
BMP с выравниванием строк, число потоков больше высоты и отказ на повреждённом файле.
Также проверено, что пакетная обработка не перезаписывает существующие результаты.
Проверки проходят командой `python -m unittest discover -s tests -v`.

## Как проводятся замеры

Bash-скрипт `scripts/benchmark.sh` запускает каждую конфигурацию один раз для
прогрева, затем несколько раз для измерений. Опубликованные результаты получены для прежней цепочки из размытия, резкости и серого. В выполненных опытах использованы
три измерения и 1, 2, 4, 8 потоков. Генерация изображений не входит во время обработки.

Измеряются чтение, цепочка фильтров, запись и общий цикл. Отдельно показываются
время вычислений и время вместе с файлами. По повторениям берётся медиана.
Ускорение равно `T₁ / Tₚ`, эффективность — ускорение, делённое на число потоков.
Для всех режимов база сравнения — `file-first` с одним потоком на том же наборе.

Численные результаты, исходные CSV и график находятся в [results/RESULTS-3-filters.md](results/RESULTS-3-filters.md).
Это замеры синтетических данных на конкретном компьютере, а не гарантия такого
же ускорения на любых изображениях и оборудовании.

## Загрузка CPU при обработке папки

Для повторного опыта сгенерировали 100 BMP размером 320×180 (seed 42). Оба запуска `pipeline` читали одну папку. Для каждого числа потоков выполнили один прогрев и три измерения со свежими выходными файлами. Сборка Windows через `build.cmd`, 8 логических процессоров.

| Потоки | Чтение, мс | Фильтры, мс | Запись, мс | Всего, мс | Занято процессоров при фильтрации | Занято процессоров за весь цикл |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 46,1 | 624,3 | 267,4 | 947,9 | 0,99 | 0,87 |
| 8 | 29,4 | 101,9 | 192,8 | 320,9 | 6,81 | 2,58 |

Число занятых логических процессоров — отношение суммарного процессорного времени всех потоков программы (пользовательского и системного) к длительности того же интервала. Для каждого столбца приведена медиана трёх повторов. Отношения рассчитаны внутри каждого повтора. При 8 потоках программа использовала около 85% мощности восьми логических CPU во время фильтрации и 32% за весь цикл. Чтение и запись выполняются последовательно. [Исходные замеры](results/batch100/cpu.csv)

В прежней серии при 1 потоке фильтры заняли 376,3 мс из 562,8 мс, при 8 потоках — 88,1 мс из 299,8 мс. Разность последних двух медиан даёт приблизительно 212 мс, или 71% общего времени, на чтение и запись. Во второй серии при 8 потоках запись также заняла больше времени, чем фильтрация. Переход с 1 на 8 потоков сократил время фильтрации в 6,1 раза, а время всей обработки — в 3,0 раза. [Замеры прежней серии](results/batch100/raw.csv)

Для воспроизведения создать набор один раз и повторять команду обработки с отдельным выходным каталогом для каждого запуска, меняя число потоков между 1 и 8.

```bash
python scripts/generate_dataset.py benchmark-data/cpu100 --count 100 --width 320 --height 180 --seed 42
./filter --batch benchmark-data/cpu100 benchmark-output/cpu-1-run1 pipeline 1 --cpu-csv
./filter --batch benchmark-data/cpu100 benchmark-output/cpu-8-run1 pipeline 8 --cpu-csv
```

Флаг `--cpu-csv` добавляет к обычной CSV-строке два поля в миллисекундах: процессорное время всего цикла и процессорное время фильтрации.

## Развитие проекта и подготовка к защите

Дальнейшие эксперименты могут включать раздельные замеры фильтров, большие папки Full HD и 4K и реальные фотографии. Для защиты остаётся подготовить демонстрацию и распределить выступление между участниками.

## Ограничения текущей версии

Все изображения набора загружаются в память до обработки. Объём набора ограничен
доступной оперативной памятью. Для больших каталогов полезным дальнейшим
улучшением будет загрузка порциями, но в заявке это отдельно не требуется.

Поддерживается только несжатый 24-битный BMP с положительной высотой.
Форматы JPEG/PNG и другие разновидности BMP не входят в текущую реализацию.
Чтение и запись последовательные, как предусмотрено заявкой.

Файловый кеш прогрет повторными запусками. Сохранение измеряется без принудительного
сброса кеша на физический диск. Накладные расходы на создание потоков включены
во время фильтрации. Поэтому на небольших кадрах дополнительные потоки могут
замедлять выполнение — это тоже результат эксперимента.

Текущие результаты цепочки из пяти фильтров доступны в [отчёте последнего запуска](results/RESULTS.md).
